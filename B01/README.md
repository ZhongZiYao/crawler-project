# B01 — 为什么这个站点最难爬（简要分析与应对）

本目录为针对目标站点的爬虫实现（见 `main.py` 中的 `CMBWMSpider`）。下面给出对比性结论、代码中观察到的反爬手段及实用的应对建议，供学习参考。

**简要对比**
- 该仓库下的各项目（A01、A03、A05、c01…等）分别针对不同机构/页面实现爬虫；多数项目直接解析静态页面或使用简单的请求 + HTML 解析。
- `B01` 难度最高：页面强依赖浏览器渲染、API 与下载链路为动态生成或受会话保护，单纯发请求难以稳定拿到文件。

**代码中能直接看到的反爬特征（证据）**
- 使用真实浏览器驱动：`from DrissionPage import ChromiumPage`，脚本通过浏览器打开页面并模拟点击，而非仅用 requests，说明页面依赖 JS 渲染或需要登录会话。
- 监听网络请求而不是直接调用 API：代码大量使用 `page.listen.start(...)`、`page.listen.steps()`，并根据接口片段（如 `qryAnnouncementList/01`、`getPrdDocumentDownloadUrl`、`/prodDoc/download/post/`）从网络包里取 JSON 或文件字节。这表明下载流程需要在浏览器上下文中由前端触发才能得到有效的、一次性或签名的资源链接。
- 页面交互驱动：脚本通过点击标签、点击搜索、点击列表项来触发后端接口，说明服务端可能检查 `Referer/Origin/会话/操作顺序`。
- 富文本与二进制两种路径：部分条目通过 `richText` 字段直接返回 HTML（脚本将其转为 PDF），另一些通过服务端接口返回文件字节流，说明文件下载可能是有状态或需要临时授权的 POST 接口。
- 有明显的防抖与容错处理：随机睡眠、重试机制、超时回退（`PAGE_FALLBACK_WAIT_SECONDS`、`REQUEST_RETRY` 等）暗示站点存在速率限制、间歇性失败或防爬触发。

**推断的反爬/保护手段**
- JS 渲染与前端分页：数据通过前端 XHR 请求加载（非直接静态 HTML），需在浏览器环境执行 JS。
- 会话/签名保护：下载链接或 API 由前端在用户会话下签名或短时生成（一次性 URL、临时 token、Referer 校验）。
- 顺序/行为检测：服务端可能检测是否通过 UI 交互触发（点击、搜索），而非直接请求 API。
- 反自动化指纹/Headless 探测：站点可能检测浏览器指纹、无头模式或脚本特征，因而脚本选择使用 ChromiumPage（真实浏览器上下文）来降低被识别概率。
- 速率限制与封禁：需要随机间隔与重试逻辑，提示存在请求频率、并发或异常行为限制。

**实用的应对建议（学习要点）**
1. 在浏览器环境中驱动并监听网络：像当前实现一样使用 Playwright/Chromium + CDP 捕获网络响应，能拿到真实的 JSON 和文件字节，绕过签名/短链限制。
2. 模拟真实用户行为：执行点击、输入、等待渲染、随机延时，保持合理的操作节奏，避免触发速率/行为检测。
3. 保持并复用会话（Cookies/LocalStorage）：登陆或首次访问时保存 cookies，后续复用可以减少重复认证或降低被挑战概率。
4. 捕获并复用短期授权：若下载需先请求 `getPrdDocumentDownloadUrl` 再访问 `/prodDoc/download/post/`，最好在浏览器中触发并直接从网络包里抓到最终字节流，或复用服务端返回的临时 URL 和必要头部。
5. 避免直接逆向复杂签名（除非充分理解签名算法）：很多签名/加密是和页面状态、时间戳、随机数绑定，重现成本高且易被封；优先使用浏览器驱动监听再下载。
6. 注意反指纹/反 headless：使用带用户数据目录或人类行为的浏览器实例，必要时用 stealth 插件或配置（避免标准无头特征）。
7. 兜底与容错：实现重试、回退等待、下载后校验文件大小、记录已下载以支持断点续抓（`downloaded.txt` 模式）。
8. 合法合规与礼貌爬取：遵守目标站点 robots 与服务条款；控制并发、加延迟、并在必要时联系站点方获取授权。

**可继续的学习/改进方向**
- 用 Playwright/DrissionPage 的 network log 做更细粒度的参数审查，记录请求头对比，尝试分析哪些请求字段必需（例如特定 Cookie、X-CSRF-Token、Referer）。
- 若目标 API参数可稳定复现且不依赖短期签名，可尝试构造请求直接调用接口以提速；否则保留“浏览器触发 + 捕获”方式以保证可靠。
- 研究如何安全地使用代理池/速率控制以避免 IP 被封。

**查看实现**：主要逻辑在 [B01/main.py](B01/main.py#L1)，类名 `CMBWMSpider`。

# 招银理财公告爬虫（B01）

本项目用于抓取招银理财信息披露页面中的“公募产品公告”6个模块：

- 发行公告
- 定期报告
- 到期公告
- 产品说明书
- 产品相关协议
- 其他产品公告

并按公告类型分目录下载文件，生成统一日志，支持失败重试与断点去重。

## 1. 目录结构

- `main.py`：主脚本
- `requirements.txt`：依赖
- `download_files/`：下载根目录（自动创建）
- `download_files/downloaded.txt`：去重记录（按来源链接）
- `download_files/crawl_state.json`：断点与失败任务状态（自动维护）
- `招银理财_日志记录.csv`：下载日志（成功/失败都记录）

## 2. 环境与安装（使用 B01 的 uv 虚拟环境）

在 `B01` 目录执行：

```powershell
uv pip install --python .\.venv-B01\Scripts\python.exe -r requirements.txt
```

## 3. 运行

```powershell
.\.venv-B01\Scripts\python.exe .\main.py
```

## 4. 已实现规则

1. HTML 富文本公告会转为 PDF 保存。
2. 下载失败不终止程序，单条下载重试 3 次，每次等待约 3 秒；翻页/下载链路未拿到时额外等待约 10 秒再重试。
3. 代码中“需手动修改”参数已在 `main.py` 顶部配置区标注。
4. 文件命名规则：`机构名 + 产品名 + 公告类型 + 产品代码(如有) + 销售代码(如有)`。
5. 当产品代码/销售代码缺失时，不拼该字段，不会生成“未命名占位段”。
6. 每次运行先重试历史失败案例，再继续新任务。
7. 自动记录断点（页号 + 条目序号），下次优先从断点继续，并尝试直接跳页。
8. 单个模块全部完成且无失败遗留时，下次运行自动跳过该模块。
9. 二进制下载仅使用“页面触发 + 网络监听字节流”方式，避免直连下载带来的文件损坏风险。
10. 成功与失败都写入日志，便于回溯补全。
11. 用来源链接去重，重复来源自动跳过；同名文件自动追加 `_1`、`_2`。
12. 下载文件按公告类型分别存入子目录。

## 5. 日志字段

日志字段与规则如下：

- 机构名称：统一使用 `招银理财`
- 公告名称：完整标题并去除多余空格
- 公告类型：固定分类（6个模块）
- 披露日期：`YYYY-MM-DD`
- 下载时间：`YYYY-MM-DD HH:MM:SS`
- 状态：`SUCCEED` / `FAILED`
- 来源链接：下载最终链接或富文本标识链接
- 保存路径：成功写实际路径，失败写期望路径
- unique_key：`机构名称 + 公告类型 + 公告名称 + 披露日期`

## 6. 说明

- 该站点请求体含前端加密字段，脚本采用浏览器自动化 + 网络监听方式抓取列表与下载链路，稳定性高于纯 requests 直连。
- 若站点前端改版（class 名变化），需更新 `main.py` 中的 CSS 选择器（`.tittleItem`、`.listBox .item`、`.btn-next`）。

## 7. 从指定页开始

在 `main.py` 顶部配置区可设置：

- `START_PAGE = 1`：全局起始页（默认从第 1 页）。
- `START_PAGE_BY_NOTICE_TYPE = {}`：按模块设置起始页，优先级高于 `START_PAGE`。

示例：

```python
START_PAGE = 1
START_PAGE_BY_NOTICE_TYPE = {
	"发行公告": 120,
	"定期报告": 35,
}
```

脚本会优先尝试“直接跳页”；若页面结构不支持，会自动回退为快进翻页。

## 8. 断点与失败状态

- 状态文件：`download_files/crawl_state.json`
- `modules`：记录每个模块是否完成、当前断点页和条目序号
- `failed_items`：记录下载失败案例；下次运行优先重试
